# Handle-bound token observation

`TokenObserver.Observe` only accepts an already-held `SafeProcessHandle`, expected PID, exact creation FILETIME and expected absolute image path. It does not open a PID or discover a process tree. The caller must first establish that the handle belongs to an approved test-owned process and independently identify its role. The handle must remain open during the call and grant `PROCESS_QUERY_LIMITED_INFORMATION` and `SYNCHRONIZE`; token access requests only `TOKEN_QUERY`. Process exit, stale identity, access failure and missing information return `INCONCLUSIVE`.

The observer records integrity RID, AppContainer flag, group and deny-only counts, restricting-SID count, enabled privilege names and counts, and—if the OS permits—job membership and Win32k system-call-disable status. `TokenRestrictedSids` reports a list of restricting SIDs; a zero count does **not** establish that the token has no other restrictions. `IsTokenRestricted` also checks only that list and returns zero on error, so it is not treated as a complete or independently authoritative restricted-token test. Group SIDs, command lines, file contents and credentials are not recorded. Counts and output are bounded.

`OBSERVED` means only that the handle identity checks and a point-in-time token snapshot succeeded. Every result retains `ProcessRole=NOT_ESTABLISHED` and `SandboxEnforcement=INCONCLUSIVE`. A matching path is not a mapped-image hash and cannot defend against a hostile local administrator or concurrent replacement. A token may change after snapshot, including during delayed sandbox lockdown. Missing job or mitigation information remains unknown; job membership alone is not evidence of job restrictions. The observer does not prove browser/renderer lineage, full descendant coverage, desktop restrictions or packet enforcement.

The pinned [Chromium 154 Windows sandbox implementation](https://github.com/chromium/chromium/blob/154.0.8037.98/sandbox/policy/win/sandbox_win.cc#L213-L224) configures low then delayed untrusted integrity and token restrictions, and its [renderer policy](https://github.com/chromium/chromium/blob/154.0.8037.98/sandbox/policy/win/sandbox_win.cc#L544-L576) includes Win32k and job restrictions. Applicable policies can vary with platform and feature state; a single snapshot, low integrity or AppContainer status alone is not proof of the complete Chromium sandbox. [Microsoft documents the limited meaning of `IsTokenRestricted`](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-istokenrestricted).

Run the tests on Windows with `dotnet run --project tests/research/p309g/TokenObserver.Tests -c Release`. They query only their own process and an already-exited test-owned child. They are API and failure-path tests, not renderer-token evidence.
