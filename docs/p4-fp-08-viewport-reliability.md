# Viewport letterboxing reliability

P4-FP-08 starts from draft PR [#71](https://github.com/roshan-pandit1/AegisBrowser/pull/71), commit `96264aaaf1a72c790ee7e07018b5d2ad24853dd2`. The production runtime remains .NET 8, CefSharp 154.0.340 and Chromium 154.0.8037.98. Letterboxing remains a profile-local, default-off setting applied after profile restart; native popups are outside the tab layout.

## Baseline

The unchanged parent was run locally in a new disposable profile on Windows ARM64 with x64 CEF emulation and effective `DeviceDpi=96`. Its write process passed 120 checks and its restart/read process passed 99; both exited 0 and reported CEF shutdown. With letterboxing enabled, zoom +1 used a 960×600 control and exposed `innerWidth=800`, `innerHeight=500`, `clientWidth=787`, and `visualViewport.width` approximately 787.5. At zoom 110%, an 880×550 control exposed an 800×500 inner viewport. At zoom −1, a 1000×583 control exposed 1200×699, with a visual height approximately 699.6. These are bounded loopback-fixture results, not measurements of actual display scaling or general website compatibility.

Two intermediate P4-FP-07 local runs timed out waiting for a letterboxing-disabled form to close after a zoom reset, while the polling timer was inactive. A renderer-settled barrier did not establish the cause. Subsequent parent local and hosted workflows passed. Separately, an intermediate enabled-only experiment disposed CefSharp's cached browser-owned host wrapper; the earlier milestone removed that disposal before its successful tests. The unrelated historical SOCKS callback timeout also remains unexplained. See the [P4-FP-07 report](p4-fp-07-zoom-letterboxing.md).

## P4-FP-08 implementation and test scope

The viewport calculation and zoom-query lifecycle are revised in `AegisBrowser.Core/ViewportLetterboxing.cs`, `AegisBrowser.Core/ViewportZoomQuery.cs` and `AegisBrowser/MainForm.cs`. The existing `GetBrowserHost()` wrapper is owned by CefSharp and is not disposed by the zoom poller. After a three-second monotonic deadline, the coordinator discards its pending-task reference and suppresses replacement requests for that browser until the tab is retired. This does not cancel the underlying CEF operation. A result first observed after the deadline is conservatively discarded even if it completed before the deadline while the UI was delayed. Other tabs remain independent; late faults are observed, pending navigation and background-tab results are invalidated, and background timeouts are checked without starting new background requests. Completed failures are retried after a three-second delay; tab or window closure retires query state.

The proposed geometry considers integer control sizes around a CSS bucket to reduce discrepancies introduced by Chromium's observed integer viewport rounding. It does not inject scripts or measure and resize repeatedly based on page content. Actual renderer behavior must be measured; an integer control dimension, Windows DPI scaling, browser zoom, or a geometry calculation by itself does not prove a particular CSS result.

The local core suite passed, including 44 zoom-query checks and 24,051 geometry checks. One earlier geometry-test attempt failed on a 110% floating-point boundary; the calculation was corrected and the suite rerun successfully. The actual CEF fixture passed 158 write checks and 119 restart/read checks on Windows ARM64 under x64 emulation at effective DPI 96. Both processes exited 0 and reported CEF shutdown. The write fixture exercised a test-injected stalled task, unrelated-tab navigation, late completion after tab closure and window closure with a pending task. This demonstrates application behavior under a synthetic stall; it does not establish why a real CEF operation would stall. Final-head Windows CI is pending.

The first P4-FP-08 implementation run passed its 158 write-process checks and native shutdown, and measured a 1200×700 inner viewport at zoom −1 with a 1000×584 control. Its restart/read process failed waiting for a change to zoom +1: the preceding tab-close stress had already left Chromium's per-origin zoom at +1, so the requested change did not change the measured width. The fixture now explicitly resets its initial zoom after navigation. This preserves the failed attempt and tests configuration persistence independently of an uncontrolled prior origin zoom.

In the corrected local run, zoom −1 produced 1200×700 from a 1000×584 control, compared with the parent's 1200×699 from 1000×583. Zoom +1 produced 800×500, 110% produced 800×500, zoom +2 produced 600×400, and zoom −2 produced 1401×800; the latter remains one pixel from the nominal width bucket. The last local +1 measurements settled in 598 ms on write and 666 ms on read, including fixture stabilization waits; these are observations, not latency guarantees.

At zoom 0 in the enabled fixture, no forced scrollbar gave inner/client/visual dimensions of 1200×700. A vertical scrollbar gave a 1185×700 client viewport, a horizontal scrollbar 1200×685, and both 1185×685; the inner viewport stayed 1200×700. The test changes only controlled page CSS, not browser APIs or production scrollbar behavior. Other display configurations and pages can differ.

## DPI, privacy and compatibility

The baseline's effective DPI 96 is not independent proof of a configured Windows scaling percentage. Actual 125%, 150%, 200% and mixed-monitor configurations are **NOT_RUN**. Scrollbars can make `documentElement.clientWidth` and `visualViewport` differ from `innerWidth`; results for each must be reported separately. Native popups remain outside this layout.

Sizing remains asynchronous. A page can observe an earlier viewport during startup, navigation or after zoom changes; a background tab is refreshed when selected. A timed-out, uninterruptible CEF request does not become cancelled simply because application state discards it. The control may require closing and reopening a tab to restore its zoom adjustment after a timeout. Smaller panes can be below the first bucket, and integer dimensions can make exact CSS sizes infeasible. Centered margins reduce browsing area and can change responsive layout.

This feature does not hide `screen` dimensions, the IP address, or other font, Canvas, graphics, audio and browser signals. It does not establish anonymity or full fingerprint resistance. The existing sandbox, TLS validation, CefSharp pins, permissions, popup ownership, profile leases and `ProxyRepository.EnsureRuntimeReady` guard must remain unchanged. Record any failed or inconclusive native test rather than treating a passing retry as a root-cause finding.
