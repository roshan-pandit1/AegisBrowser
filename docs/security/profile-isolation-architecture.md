# Profile-specific network identity: research decision

Status: **candidate for controlled investigation only**, 2026-10-31; baseline `88c4f1821e6f4217bca151033f464e14e02b4136`. No candidate is yet proven safe with CefSharp 154, so required-proxy startup stays blocked. A native prototype may establish feasibility; it must not be connected to production startup or weaken the existing guard.

## Decision

Investigate a unique per-profile Windows AppContainer security identity, installed and verified before a suspended browser is resumed, combined with narrowly scoped WFP policy and an authenticated local broker. A job object may assist lifecycle observation. This is a hypothesis: it is not a selection of an implementation ready for deployment. If native tests show the CEF subprocess tree cannot be kept under the identity, or policy cannot survive failures without affecting other software, reject this candidate and evaluate isolation in a separately managed VM. Do not add a kernel driver without a separate signing, deployment, maintenance and security decision.

| Candidate | Security and process identity | Compatibility, privileges and failure behavior | Decision |
| --- | --- | --- | --- |
| AppContainer + WFP | A package SID can be a profile-specific classification input; actual identity of every Chromium child and delegated resolver remains unverified. Restrict IPC and handles too. | AppContainer can restrict file, registry, GPU and IPC access; CEF's sandbox may create differently scoped tokens. User-mode WFP management needs appropriate BFE ACL rights, normally an elevated installer/service. x64 and ARM64 unverified. | Preferred research candidate, not production approved. |
| Broker with PID/process-tree tracking | Can associate an owned process handle and creation identity with a profile, but observation after child creation has a race and PID reuse makes PID alone unsafe. | Broker authentication, handle lifetime and child creation need native testing. Cannot by itself enforce network policy before every child runs. | Orchestrator only, never the sole boundary. |
| Job object | Tracks a process group under applicable creation/breakaway rules; it is not an outbound destination firewall. | Child association has documented exceptions, including `Win32_Process.Create` and breakaway. CEF sandbox/job compatibility and any kill-on-close behavior are unverified. | Optional lifecycle aid; never proof of containment. |
| WFP application path or Windows account | All current profiles share these values, so such filters cannot separate them. A PID in event metadata is not automatically an available user-mode filter condition. | Broad rules could affect unrelated profiles and apps. WFP rights and policy conflicts matter. | Reject as sole profile identity. |
| Per-profile VM with controlled egress | A separate OS/network boundary can separate workloads if implemented correctly. | Requires a guest, lifecycle, updates, licensing, configuration, IPC and independent network tests; materially higher resource and deployment cost. ARM64/guest support unverified. | Fallback for separate feasibility and threat review. |

## What Windows documents, and what it does not prove

[WFP ALE](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-) authorizes socket and connection operations. Microsoft's [layer-condition table](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-conditions-available-at-each-filtering-layer) lists `FWPM_CONDITION_ALE_PACKAGE_ID`, protocol, address and port at outbound `ALE_AUTH_CONNECT_V4/V6`; [the identifier](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-) is an AppContainer SID. Resource-assignment layers expose different conditions. Choose layers only after tests of actual TCP, connected/unconnected UDP, loopback, IPv6 and delegated DNS; a condition's presence does not prove full egress coverage. Microsoft documents [filter arbitration](https://learn.microsoft.com/en-us/windows/win32/fwp/filter-arbitration), including interaction between sublayers and terminating actions; a generic allow plus deny is not automatically correct.

[`PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) can request AppContainer process creation. [CreateAppContainerProfile](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile) manages named identities; creation, ACLs and cleanup require their own review. Microsoft describes restrictions on AppContainer processes and children, but that does not verify CEF's alternate sandbox tokens, helper services, handles or network-service behavior for this build. [Job object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) child inheritance is conditional. Record actual process token/package SID, architecture, creation time, executable role and retained process handle in native tests; no credentials or private browser content.

[Chromium's public Windows sandbox source](https://chromium.googlesource.com/chromium/src/sandbox/+/61ba54e9a2ac3c471318e48ba8f0bdaaf03eedd6/policy/win/sandbox_win.cc) includes separate AppContainer/LPAC handling and capabilities for a network sandbox. This is evidence that child-token behavior needs investigation, not proof that the pinned CEF binary uses that exact source or configuration. The pinned CefSharp package is `154.0.340`; obtain its exact CEF/Chromium revision and inspect and measure that build before relying on any upstream behavior.

The separate test-only `tests/acceptance/observe-cef-process-identity.ps1` starts a synthetic CEF fixture and reads process-creation times, machine types and AppContainer token information from another process. It verifies its reader against itself, an invalid PID and a synthetic child. The CEF test briefly waits for the observer and then follows its normal shutdown path. A point-in-time process tree can miss short-lived or differently parented children, or associate a recycled PID; this observer is diagnostic only and does not demonstrate containment, startup ordering, WFP enforcement or complete coverage. It installs no rules or AppContainer identities. An inaccessible process is reported as inconclusive.

In [Windows x64 run 41181772736](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/41181772736), the synthetic browser and five observed `CefSharp.BrowserSubprocess.exe` children reported `TokenIsAppContainer` false. That is one snapshot of the existing configuration, not an inventory of every process role or evidence about launching CEF inside an AppContainer.

The separate `research-appcontainer-launch.ps1` experiment derives two synthetic SIDs, optionally registers their per-user AppContainer profiles on a disposable GitHub-hosted runner, and tries to create fixed `cmd /c exit` control processes suspended with those security capabilities. It reads the actual token before resuming the controls. It does not launch CEF, add firewall rules, authorize networking or prove child inheritance. Registration creates per-user Windows profile data; the opt-in switch refuses non-GitHub-hosted runners and leaves those synthetic identities to disposal of the runner, without deleting any existing profiles. Without registration on the development ARM64 host, SID derivation succeeded but synthetic process creation returned Win32 error 2; the cause and behavior on another Windows build are unverified.

In [Windows x64 run 41262862195](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/41262862195), two registered synthetic identities produced distinct SIDs. The observer read the requested AppContainer SID from each suspended control process before resume, and both commands exited normally afterward. This establishes that narrow primitive in that environment; it does not test a browser, subprocess inheritance, WFP, networking or service failure.

WFP objects in a [dynamic session](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_session0) are removed when the session ends. Therefore, a browser continuing after its service/session dies could lose the only deny rule. Killing a job after service death alone can race that loss; it is not sufficient evidence of fail-closed behavior. A durable, tightly scoped default-deny policy plus separately managed temporary permissions is one hypothesis, subject to proving boot/BFE/restart behavior, ownership, arbitration, unrelated-app isolation and safe recovery. Do not install such persistent rules on a user's machine as part of this research.

## Proposed lifecycle and unresolved gates

1. Validate the profile, path and stored proxy policy, acquire the existing lease, and check credentials without logging them.
2. In an isolated test environment, allocate a distinct synthetic identity. Authorize only the specific test proxy endpoint and necessary test IPC; do not infer that all loopback or DNS is safe.
3. Use a broker with owner-authenticated IPC and minimal delegated BFE rights. Install a complete atomic test policy, inspect the actual committed objects and verify independently that restrictions are effective. If any step fails, do not start the profile.
4. Create the target with the intended security capabilities suspended, retain its handles and verify the token. Resume only after policy verification. Suspension does not prove that spawned or separately brokered descendants are covered.
5. Continuously detect policy loss and child identity deviations; define and test a fail-safe mechanism that does not depend on racing dynamic filter removal. On graceful shutdown, preserve CEF's existing native release order and lease lifetime; remove only demonstrably owned policy after all network-capable processes have exited.
6. Inject broker/BFE failure, network changes and PID reuse; independently measure traffic. A missing event or packet is inconclusive without healthy positive controls.

No production privileged component, installer, ACL change, rule or recovery command exists. See [recovery](containment-recovery.md) and [test plan](network-egress-test-plan.md).

## Windows versions and architectures

The existing deliverable and Windows CI target x64. On the ARM64 development host (Windows build 26300), a small x64 .NET 8 process ran under emulation and read its own token. Its runtime reported x64 on ARM64, while `IsWow64Process2` returned `0x0000` for the process machine and `0xAA64` for the native machine. Treat these as raw API values: [Microsoft defines zero](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-iswow64process2) as `IMAGE_FILE_MACHINE_UNKNOWN`, not proof that the target is a native ARM64 binary. This observation does not establish CEF or WFP behavior. [Microsoft documents](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation) x64 user-mode emulation on Windows 11 Arm; kernel drivers must be native Arm64. Independently test x64 Windows and Windows 11 ARM64 with x64 CEF, including GPU, helper tokens, WFP and recovery. No ARM64 support claim follows from x64 CI.

An offline-built x64 CEF proxy probe on that ARM64 host observed the controlled HTTP route and direct loopback STUN and reached native host-release checks, but the overall run failed before its HTTPS fixture when Windows certificate creation raised `CryptographicException` with error 2. Chromium also reported that encryption was unavailable. The cause is unverified in this sandboxed environment; these partial observations do not establish TLS behavior, session persistence or ARM64 product compatibility. No real user profile or credential was used.
