# AppContainer private-network capability research

This is a test-only investigation. It does not change browser startup, configure a proxy, add a firewall rule, or establish profile-specific network containment. Required-proxy profiles remain subject to the existing production startup guard.

## Capability and token construction

The research launcher requests only Windows' well-known `privateNetworkClientServer` capability for its fixed synthetic client. It constructs the SID using `CreateWellKnownSid` with `WinCapabilityPrivateNetworkClientServerSid` (87), and expects `S-1-15-3-3`. This is the built-in SID derived from the application-package authority and private-network capability RID. It places that SID in a single `SID_AND_ATTRIBUTES` entry with `SE_GROUP_ENABLED`, supplies the entry and the synthetic package SID in `SECURITY_CAPABILITIES`, and creates the client suspended with the process security-capabilities attribute.

This capability is broad private-network authority, not an allowlist for a particular peer. It applies to home/work network access according to Windows networking policy; an RFC 1918 address by itself does not prove that the network is classified as private or that a connection is permitted. It does not establish DNS, UDP, WebRTC, IPv6, proxy, or WFP behavior. Its use is confined to explicitly isolated test infrastructure and is not a production permission decision. See Microsoft's [capability SID constants](https://learn.microsoft.com/en-us/windows/win32/secauthz/capability-sid-constants), [AppContainer launch guidance](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), and [app capability declarations](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations).

Before permitting resume, the launcher queries the retained process token for AppContainer status and its package SID, comparing that SID with the identity requested for the synthetic test. It then queries `TokenCapabilities` and requires exactly one capability: the expected SID must be enabled and not deny-only. Missing, unexpected, disabled, or unqueryable capability state rejects verification. A failed verification clears the permission to resume; the caller must dispose the owned process handle in a `finally` block so an unverified suspended process is terminated. The token query uses native structure alignment for `TOKEN_GROUPS` rather than assuming a pointer offset. See [token information classes](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_information_class) and [SID attributes](https://learn.microsoft.com/en-us/windows/win32/secauthz/sid-attributes-in-an-access-token).

The capability-enabled entry point accepts a synthetic identity and matching owned test directories, and runs only the fixed test-executable mode. The token-only hosted-runner fixture creates temporary synthetic files and an AppContainer identity, verifies the suspended token, tests rejection of invalid identities and paths, and disposes the process without resuming it. It neither sends traffic nor changes system network policy. Synthetic identity and files are retained until disposal of the hosted runner; no real browser profile or credential is used.

## Evidence and limits

**Native execution:** [Windows x64 CI run 41314237304](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/41314237304) passed at commit `25304b72693de5b25665266a9aa2a4e737182aac`. Before resume it verified synthetic PID 6436's requested package SID and sole enabled capability SID `S-1-15-3-3`, rejected invalid identities and linked paths, and disposed the process without resume. No network attempt was made. **Cross-VM network delivery:** not executed. A successful token check does not prove that a receiver can be reached, and a connection timeout does not prove WFP enforcement. The earlier zero-capability loopback result remains inconclusive; it does not establish a root cause. No privileged WFP filtering or process-to-flow attribution is part of this test.

The subsequent network gate requires an authorized, pre-provisioned isolated two-machine environment, a known private-network endpoint and independent receiver, an ordinary-client positive control, and then an AppContainer positive control using the verified capability. Do not add a global loopback exemption or change ordinary workstation networking to obtain this evidence. If the environment or either control is unavailable, record the relevant gate as blocked or inconclusive; leave production routing disabled.
