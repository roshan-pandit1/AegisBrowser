# WFP packet-decision attribution research

**Status: NOT EXECUTED.** This is a proposed observation method, not an implemented packet-enforcement test. The independently received nonce proves only that the receiver got a message; it does not establish which OS process sent it. WFP object readback likewise does not prove that the object blocked a packet. No test below authorizes running a capture on a normal workstation.

On an explicitly authorized disposable Windows test VM, a future observer can investigate subscribing to WFP network events with [`FwpmNetEventSubscribe4`](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmneteventsubscribe4), which requires `FWPM_ACTRL_SUBSCRIBE` access. Microsoft's [firewall troubleshooting example](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/troubleshooting-uwp-firewall) shows a classify-drop event containing a filter ID and layer as well as package identity and network metadata. The subscription and event structures are version-specific; support, permissions, event availability, and behavior must be checked on the target Windows build.

For each synthetic attempt, retain the process handle while the test runs, verify its AppContainer token before resume, and record its creation time and expected package SID. If a classify-drop event is available, independently compare its filter ID to the ID returned by the test-owned WFP filter, its layer to the intended layer, and its packet direction, timestamp, protocol, endpoint and package SID to the attempt. Honor [`FWPM_NET_EVENT_HEADER3` validity flags](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_net_event_header3): missing flags mean those corresponding fields are unavailable, not matching defaults. Record the owned provider, sublayer, filter key and runtime filter ID for the duration of the session. Reject ambiguous, late, missing, mismatched or unattributable observations as **INCONCLUSIVE**.

The documented event header does not itself expose a process ID. A matching package SID, executable app ID and network tuple can provide policy-decision evidence but cannot alone prove a particular PID caused the flow. Additional supported process/flow telemetry and lifetime correlation would require separate validation, including PID reuse, transient Chromium children, event loss and clock skew. A result cannot be called **VERIFIED_BLOCKED** unless the chosen evidence actually establishes the claimed association, the unfiltered positive control is independently observed, the unrelated-identity control succeeds, and cleanup restores the baseline.

Event subscription, engine options or tracing may require privileges and may collect metadata about unrelated traffic. Restrict experiments to synthetic identities and an isolated disposable machine; bound capture duration and retention, avoid packet contents or credentials, and examine what an instrumentation method captures before using it. Do not modify global collection settings on the developer's host. Microsoft states that [`FwpmEngineSetOption0` network-event collection settings persist across reboots](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmenginesetoption0); do not assume session disposal rolls them back. If a prerequisite is unavailable or event collection cannot be scoped safely, stop and record **BLOCKED** or **INCONCLUSIVE**, rather than assuming that a missing event means a block.

An effective packet decision for a test fixture would still not establish coverage for all CEF subprocesses, IPv6, UDP, DNS, WebRTC, proxy outages or policy-owner failure. Production proxy-required startup remains blocked.
