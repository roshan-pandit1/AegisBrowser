# Independent TCP positive-control research

This test-only fixture is not WFP enforcement. An independent parent process owns an IPv4 loopback listener, registers random synthetic transaction identifiers, and records only matching bounded messages. A separate ordinary synthetic client must reach it first; an unavailable receiver or failed positive control is a fixture failure. The listener does not capture every interface, identify packet owners through Windows, or prove packet absence.

The second client is the same fixed test executable launched suspended using a fresh per-user AppContainer SID. The retained process handle's token must match before resume. The client is restricted in code to TCP on `127.0.0.1` and reads only an owned synthetic control file; it does not initialize CEF. This test requests no AppContainer network capabilities and installs no loopback exemption, firewall rule, WFP filter, service, or driver. The controlled loopback attempt may fail because of AppContainer capability or loopback policy, access permissions, or fixture failure. No observed packet is **inconclusive** and is not a verified block.

An independently received matching transaction with a successful client exit is reported as `ALLOWED_AND_INDEPENDENTLY_OBSERVED`, with process-to-packet identity attribution explicitly marked unverified. Correlation does not substitute for an independently captured process/network event. The output includes a versioned JSON record with the synthetic SID, process creation time, transaction, endpoint, normal-client positive control, observation count, cleanup status and `wfpFilter: null`. It includes the client's strictly validated result or an explicit missing, unreadable or invalid marker; socket errors contain only the numeric `SocketErrorCode`. Results such as missing identity, unavailable environment or fixture failure are separate from observed delivery. Neither outcome establishes profile-specific containment.

## Initial Windows observation

On the GitHub-hosted Windows x64 runner, [run 41291245034](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/41291245034) for commit `db2d32497924a524ca2ab4ae250e37f91c183c8d` completed successfully. The ordinary client positive control reached the independent observer. The zero-capability AppContainer client had its SID verified before resume, exited with code 1, and produced zero matching observations. Its classification was `NO_PACKET_OBSERVED_INCONCLUSIVE`; no WFP rule or decision was observed. The earlier version of the experiment did not print the client result, so the reason for its exit is unknown. The normal-client result does not establish AppContainer reachability. This observation is not evidence of enforcement or packet-to-process attribution.

An unverified next experiment is a client and independent observer on two disposable VMs connected to a pre-provisioned isolated private network. Investigate granting only the synthetic client's AppContainer the `privateNetworkClientServer` capability and verify the capability as well as the SID on its suspended token before resume. Restrict the test to owned endpoints and retain positive controls. This requires a separately reviewed opt-in harness and does not justify loopback exemptions or broad firewall changes. Capability and token background: [Microsoft app capability declarations](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations) and [implementing an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer).

To run only on an explicitly opted-in disposable GitHub-hosted Windows runner after building the native x64 test executable:

    ./tests/acceptance/observe-appcontainer-tcp-control.ps1 -BrowserTestsExe ./AegisBrowser.BrowserTests/bin/Release/net8.0-windows/win-x64/AegisBrowser.BrowserTests.exe -RunOnDisposableRunner

The script uses unique test roots and SIDs, rejects linked source paths, grants access only within its new synthetic root, and leaves its identity and files for disposal with the runner. It does not touch real browser profiles or existing Windows networking settings. If a synthetic client hangs, only its own retained process is stopped. This experiment does not execute or verify WFP behavior. The existing startup guard continues to block required-proxy profiles.
