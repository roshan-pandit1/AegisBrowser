# P4-FP-04: Worker WebGL enforcement research

## Scope and starting point

This research is stacked on PR #67, `feature/p4-fp-03-cross-context-webrtc-privacy`, at `8203b7b32d6b140614c5cc048e7a64a17aedb95f`. The pinned stack is .NET 8, CefSharp.WinForms.NETCore 154.0.340, CEF 154.0.34 (`14c5a089e8452874cb1a556dc3fde26ed2d87723`), and Chromium 154.0.8037.98. The parent [push](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/43016923934) and [PR](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/43016930636) Windows x64 workflows passed.

The existing opt-in `DisableWebGl` setting is applied as `IBrowserSettings.WebGl = CefState.Disabled` before ordinary browser creation; it is off by default and changes require profile restart. P4-FP-03 observed WebGL blocked in its controlled document frames and native popup, yet functional in a dedicated worker's OffscreenCanvas. The current Privacy window and `docs/privacy.md` warn about this limitation.

## Pinned implementation boundary

1. CEF [`renderer_prefs::SetCefPrefs`](https://github.com/chromiumembedded/cef/blob/14c5a089e8452874cb1a556dc3fde26ed2d87723/libcef/browser/prefs/renderer_prefs.cc) maps disabled `cef.webgl` into false `webgl1_enabled` and `webgl2_enabled` Blink WebPreferences.
2. Chromium [`HTMLCanvasElement::IsWebGL1Enabled` and `IsWebGL2Enabled`](https://github.com/chromium/chromium/blob/154.0.8037.98/third_party/blink/renderer/core/html/canvas/html_canvas_element.cc#L591-L605) read their frame Settings. By contrast, [`OffscreenCanvas`](https://github.com/chromium/chromium/blob/154.0.8037.98/third_party/blink/renderer/core/offscreencanvas/offscreen_canvas.h#L154-L157) returns true for both enablement methods and false for its blocked check. This distinction applies to OffscreenCanvas as a host, including document-created instances; it is not limited to a worker name or origin.
3. [`WebGLRenderingContextBase::CreateWebGraphicsContext3DProvider`](https://github.com/chromium/chromium/blob/154.0.8037.98/third_party/blink/renderer/modules/webgl/webgl_rendering_context_base.cc#L725-L737) consults the host methods before provider creation. When the OffscreenCanvas overrides permit it, the [renderer platform](https://github.com/chromium/chromium/blob/154.0.8037.98/content/renderer/renderer_blink_platform_impl.cc#L676-L704) proceeds toward a WebGL GPU command-buffer provider. This source path explains why the per-browser document preference did not govern the tested OffscreenCanvas contexts.

The pinned Chromium [`content_switches.cc`](https://github.com/chromium/chromium/blob/154.0.8037.98/content/public/common/content_switches.cc#L105-L109) describes `disable-webgl` as disabling WebGL versions. [`WebContentsImpl::ComputeWebPreferences`](https://github.com/chromium/chromium/blob/154.0.8037.98/content/browser/web_contents/web_contents_impl.cc#L3593-L3606) maps it to the same document WebPreferences checked by HTMLCanvasElement. Source documentation alone does not establish worker enforcement; the experiment below checks actual behavior. The separate `disable-3d-apis` switch is mapped by that same WebContents function into those preference flags. A separate local CEF process requesting it also left WebGL 1 and 2 functional in document and worker OffscreenCanvas; it is not deployed as a fix.

[CEF settings](https://github.com/chromiumembedded/cef/blob/14c5a089e8452874cb1a556dc3fde26ed2d87723/include/internal/cef_types.h) and [pinned CefSharp settings](https://github.com/cefsharp/CefSharp/blob/ec1027aa21e1af1217681a349104c15d29bbc21a/CefSharp.Core/CefSettingsBase.cs) distinguish rejecting external Chromium command-line arguments from application-owned arguments supplied during `OnBeforeCommandLineProcessing`. A process-wide switch would apply to the application's profile process, not independently to browsers sharing that process. That mechanism's availability is not evidence that a particular switch blocks workers.

## Controlled process experiment

The experimental probe launches separate disposable CEF processes and profiles for baseline and for test-only application-supplied `disable-webgl` and `disable-3d-apis` switches before `Cef.Initialize`, while keeping external command-line arguments disabled. The controlled test pages are local scheme-handler fixtures; no API is monkey-patched and no hardware values or pixels are retained. Each WebGL version gets a new canvas, obtains its own context, and performs a bounded clear and synthetic one-pixel readback; pixel values are discarded. Missing baseline capability, a failed rendering operation, or an unavailable worker remains inconclusive rather than proof of blocking.

On the local Windows ARM64 host under x64 emulation, the default process created and rendered WebGL 1 and WebGL 2 in the tested HTML and OffscreenCanvas contexts. With the candidate process switch, HTML document WebGL 1 and 2 were unavailable, but both document OffscreenCanvas and dedicated-worker OffscreenCanvas continued to create and render WebGL 1 and 2 contexts. An initial enforcement assertion exited 1 after observing the gap. Subsequent diagnostic baseline and candidate processes each exited 0 after native browser closure and `CefShutdown`; the candidate explicitly reported `INEFFECTIVE`. Exit 0 here means the diagnostic completed, not that protection passed. The candidate therefore **did not close the gap in this environment**. It remains an experiment, not a production fix or proof of behavior on every Chromium build. The result is consistent with the source boundary above; do not promote a switch name, its declared intent, or a successful CEF initialization into enforcement evidence.

WebGPU uses a [separate graphics-provider path](https://github.com/chromium/chromium/blob/154.0.8037.98/content/renderer/renderer_blink_platform_impl.cc#L763-L807). Its adapter availability must be reported from the actual fixture and is not implied by either WebGL setting. Canvas 2D and its readback remain available in the controlled capability fixture; this is a compatibility observation, not Canvas fingerprint protection. Shared-worker, service-worker, out-of-process iframe and broad real-site compatibility require their own evidence. The parent native popup test is evidence for its controlled popup only.

## Decision and security boundaries

No candidate process-wide graphics flag is enabled in production by this research. The existing opt-in WebGL setting, restart behavior and worker warning remain in place. No package pin, Chromium sandbox, TLS validation, origin permission, native popup ownership, or `ProxyRepository.EnsureRuntimeReady` guard is changed. The investigation does not establish complete fingerprint resistance, network containment, or production readiness.

The next separately reviewed engineering step is to evaluate propagating an explicit, appropriately scoped graphics policy into OffscreenCanvas host checks and worker execution contexts in a pinned Chromium/CEF build, with tests for WebGL 1/2, worker lifecycle, WebGPU and Canvas 2D compatibility. Such engine changes and binaries must remain isolated from the production browser until independently qualified. Broad GPU shutdown or a JavaScript API replacement is not an established equivalent.

## Verification status

Local baseline, `disable-webgl`, and `disable-3d-apis` diagnostic processes each exited 0 after native CEF shutdown; both switch cases explicitly reported `INEFFECTIVE`. The existing profile fixture passed 128 checks in each write and restart/read process and completed CEF shutdown. The hosted Windows x64 [push](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/43022225383) and [PR](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/43022257403) workflows passed at `b810c0df811dd631262a3f08cd58d93b23e28630`. Both candidates were ineffective against the tested worker WebGL 1 and 2 with functional document baseline controls. OffscreenCanvas 2D remained functional; WebGPU adapter outcomes were inconclusive. These are bounded research results; shared/service worker WebGL, OOPIF attribution, and broader site compatibility remain unverified. Local builds used cached packages because NuGet vulnerability metadata was unavailable. Do not report a green compilation or an unavailable baseline API as worker protection. Production readiness remains **NOT_APPROVED** and full fingerprint resistance **NOT_ESTABLISHED**.
