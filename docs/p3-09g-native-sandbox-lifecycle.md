# P3-09G: supervised native CEF research

This research is stacked on draft PR #52 at `0335094262cd2450e50b4568e62ee8e0be806561`. It does not replace production CefSharp binaries, alter browser profiles, proxy enforcement, TLS, firewall, WFP, DNS or routing. `PRODUCTION_BINDING_READINESS: NOT_APPROVED` and `OWNER_RELEASE_CONTRACT: UNSATISFIED` remain in force.

## Pins and the previous gate

The research retains CEF `154.0.34+g14c5a08+chromium-154.0.8037.98`, CEF source `14c5a089e8452874cb1a556dc3fde26ed2d87723`, `cef.sdk` 154.0.34 and CefSharp source `ec1027aa21e1af1217681a349104c15d29bbc21a`. The official minimal distribution used for this experiment has recorded SHA-256 `C81C34D048D87276F4A18F0B000206710A1709BB67DD658948B87100E1A538DA`. The pin records previously checked distribution bytes; it is not independent publisher authentication.

P3-09F's combined `BLOCKED: SANDBOX_GATE` line did not identify the failing process or predicate. Its exact root cause cannot be recovered from that trace. The experimental client now distinguishes missing opt-in, missing sandbox-information pointer and disallowed sandbox switches, with an allowlisted process-role label and no raw command line. The client still requires all gates; a pointer or self-reported setting does not prove enforcement. The pinned CEF bootstrap passes a sandbox-information structure to its client, and [CEF's Windows sandbox guidance](https://chromiumembedded.github.io/cef/sandbox_setup) requires a matching bootstrap and sandbox information for the browser and subprocesses. Child role labels are client claims, not independent process identity.

The offline fixture uses an ASCII marker in a fixed `data:` URL instead of requiring raw percent-encoded URL equality. It requires main-frame load-start and load-end for the same frame before requesting close. An aborted navigation, failed frame identity, or missing completion is not a successful fixture. The 19 fixture and gate tests are synthetic and do not invoke CEF.

## Process and token evidence

`tests/research/p309g/ProcessSupervisor` is test-only. Its `supervise` entry point requires an absolute `bootstrapc.exe`, a separately located pinned bundle manifest, and a bounded timeout. The manifest enumerates all top-level files and optional one-level locale files; unknown, missing, linked, oversized or mismatched files are rejected. A manifest hash must be independently approved: a manifest supplied by an untrusted bundle is not a trust root. File locks and path checks provide defense in depth; they do not establish mapped-image provenance against a hostile administrator or all concurrent file replacement, or cover Windows system dependencies.

The supervisor uses an argument list, not a shell, retains the parent process handle, records PID, creation FILETIME, image path and input hash, concurrently drains bounded stdout/stderr, waits on that handle and obtains the native exit code. A timeout remains `TIMEOUT`; optional cleanup targets only the retained parent handle and never establishes successful native shutdown or descendant cleanup. Child identity, process-tree coverage and sandbox enforcement are **INCONCLUSIVE**. Output truncation or invalid UTF-8 is not complete evidence. Abrupt supervisor termination and unknown descendants remain unresolved; this is not a job-object containment implementation.

`TokenObserver` queries only an already-held caller-owned handle after checking PID, creation time, path and liveness. It gathers bounded read-only token information and optional job/mitigation indicators without opening arbitrary PIDs or enabling privileges. It does not discover or identify renderers, prove mapped-image identity, establish complete process lineage, or assert sandbox enforcement. Chromium's [pinned Windows sandbox policy](https://github.com/chromium/chromium/blob/154.0.8037.98/sandbox/policy/win/sandbox_win.cc) includes token, integrity, job and mitigation restrictions with configuration-dependent behavior. One snapshot or an AppContainer/low-integrity observation alone is insufficient to prove all relevant policy and enforcement.

`result-lib.ps1` correlates the supervisor's separately emitted handle identity with its result, including exact creation FILETIME and expected executable hash. It checks actual integral exit status, capture completeness, and the fixture's observed marker order. Its input is a trusted in-memory invocation result, not authenticated arbitrary log files. Even matching markers are client-reported; renderer-token evidence, subprocess cleanup and sandbox enforcement stay inconclusive. `test-result.ps1` uses synthetic records and an owned helper process, never CEF.

## Observations and limits

On the ARM64 development host under x64 emulation, one supervised CEF diagnostic used the matching pinned bootstrap and test client. The supervisor recorded a handle-bound parent identity, then timed out and terminated only that exact parent handle. It captured `CONTEXT_INITIALIZED`, `CEF_INITIALIZE_SUCCEEDED`, `BROWSER_CREATED`, and `MAIN_FRAME_NAVIGATION_ABORTED`; stderr reported that the GPU process was not usable. No successful fixture-load completion, native close or `CefShutdown` return was observed in this attempt. Process result was `TIMEOUT`, native exit unavailable by design, and the wrapper exited nonzero. A later exact-path process snapshot found no matching bootstrap processes, but a point-in-time snapshot cannot establish complete descendant accounting. No renderer token was observed and sandbox enforcement is not established. This sandboxed client was not used to assert production CefSharp behavior or network containment.

The isolated Windows x64 workflow builds pinned inputs, executes deterministic supervisor/token/classifier/gate tests, and attempts one bounded native diagnostic. It reports a diagnostic outcome rather than declaring sandbox acceptance, and it does not upload native runtime binaries. A completed workflow is not a verified lifecycle or sandbox. Record actual final-head CI and event evidence separately in the PR; do not infer a pass from the workflow's shell exit.

Next work requires reliable independent identification of a live test-owned renderer (including PID creation time and process lineage), token and relevant mitigation observations, comprehensive descendant accounting, and an offline fixture that completes without relaxing sandbox requirements. Only after a full supervised lifecycle and sandbox evidence should popup-terminal callback work proceed. No generic `CefClient` proxy should bypass the pinned CefSharp `ClientAdapter` type assumptions described in P3-09E/F.
