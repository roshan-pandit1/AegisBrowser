# Proxy configuration foundation

The P3 foundation stores proxy configuration and credentials, provides a saved-draft editor, and offers an opt-in .NET transport preflight. It does **not** configure CefSharp networking or establish network isolation. HTTP, HTTPS and SOCKS5 are configuration values, not supported browser transports yet. There is no claim of fail-closed network behavior after a browser starts.

An existing profile with no proxy record retains its previous startup behavior. A profile with a required proxy, an interrupted proxy update, invalid proxy metadata or an unsupported proxy database version is stopped before CEF initialization. A saved Direct record expresses intent and permits startup; it does not yet force Chromium to bypass system proxy settings. Invalid proxy input never becomes Direct. The dashboard's **Proxy draft** action edits saved configuration for a closed profile and warns that saving a proxy blocks launch in this build. The **Saved proxy** column shows browser defaults, a blocked draft, or a state requiring repair; it describes stored intent, not the active network route. The editor can remove a draft and return to the existing browser/network defaults after confirmation. Configuration changes require the matching closed-profile lease, the current profile metadata snapshot and the expected proxy revision.

**Bulk proxy drafts** previews the selected registered profiles, then applies a non-secret endpoint or removes drafts after confirmation. Each profile is checked independently for a closed lease and unchanged metadata and proxy revisions; results and cancellation are reported per profile. Profiles with protected credentials are skipped and must be edited individually, so bulk actions neither share nor remove credentials. Applying a proxy draft blocks eligible profiles from launching; removing drafts permits the existing browser/network defaults. Re-preview after a completed or interrupted operation. Active browser proxy routing is not available yet.

**Proxy presets** save a versioned, reusable HTTP, HTTPS or SOCKS5 endpoint without authentication or credential references. Use the dashboard to create, edit, duplicate, search or delete presets. Selecting one in the bulk editor copies its displayed values once; the profiles are not linked to the preset and later preset edits do not change them. Preset updates use revision checks, and unsupported or corrupt preset files are preserved and reported. Presets are stored separately under `proxy-presets` and are not included in the current metadata export or backup. Do not place secrets in preset names, descriptions, labels or host fields.

## Storage and recovery

`proxy-config.sqlite3` is a separate version-1 application database under the profiles root. It contains profile and proxy GUIDs, protocol, endpoint, label, authentication requirement, opaque credential reference, timestamps and revision. It contains no username or password. It does not migrate or modify the existing profile metadata database or Chromium storage. A `.aegis-proxy-required` guard in the profile directory is created before a required configuration is committed; an explicit Direct update is committed before its guard is removed. A crash between those steps leaves startup blocked. Proxy configuration and credential changes require the existing exclusive profile lease.

If the database is corrupt, missing while a guard exists, or has an unsupported version, preserve the database, its `-journal`/`-wal`/`-shm` files and the guard. Do not delete a guard to work around a failure. Recover from a verified copy using a compatible management tool, then explicitly select Direct only if that is the desired connection. This foundation does not yet provide a proxy database backup, repair UI or automated recovery. Existing metadata backups and profile exports **do not include proxy configurations or credentials**. To prevent silent loss of required policy, metadata export, clean duplication and saving a template from a profile reject required or interrupted proxy configurations until a later portable format is implemented. Existing templates and imported profiles use the existing default connection behavior.

Older AegisBrowser versions do not recognize the guard or proxy database. Before rolling back to an older executable, explicitly return affected profiles to Direct with a compatible management tool and confirm that no operation is pending. This is a compatibility limitation, not OS-level network containment.

## Credentials

The local vault uses Windows DPAPI `CurrentUser` protection with an opaque credential GUID and profile GUID bound as additional entropy. Ciphertext is stored under `.proxy-credentials/<profile-guid>/<credential-guid>.bin`, outside Chromium profile directories and separate from SQLite. The editor does not reveal an existing password; leave both credential fields empty to retain it or enter both to replace it. When retaining authentication, changing the proxy protocol, host or port requires the credentials to be entered again. Replacement publishes new encrypted material before changing its reference; the old file is removed only after the configuration commit succeeds. If the outcome of a save is uncertain, newly written encrypted material is retained for manual inspection rather than risking deletion of a referenced credential. A failed post-commit cleanup returns a warning. Plaintext credentials are excluded from configuration, normal exports, templates and metadata backups. Neither DPAPI ciphertext nor credential references are portable exports.

DPAPI depends on the Windows user profile and may become unavailable after account or key recovery problems. A different Windows account cannot normally decrypt the data; software already running as the same user is not isolated by DPAPI. Managed username/password strings can remain in process memory. This feature does not implement browser proxy authentication, a password-reveal UI, or credential sharing between profiles.

## Optional transport preflight

In a closed profile's proxy editor, enter a trusted diagnostic endpoint and select **Test saved draft**. No external endpoint is selected or contacted automatically. The endpoint receives a request when you start the test, and its operator can observe it. Use an HTTPS URL without embedded credentials, a query string or a fragment; HTTP URLs are accepted only for loopback test fixtures. Do not put secrets in the URL path. The test holds the existing profile lease until it finishes, checks that the saved proxy revision is unchanged, and uses only the saved draft and its protected credentials. Unsaved editor changes are not tested. The test is cancellable, has a bounded timeout, and the last result is shown only while the editor remains open.

This is an independent **.NET HTTP transport** test, not a Chromium test or a guarantee of browser isolation. It uses the selected proxy without an environmental bypass, normal TLS certificate validation, no browser cookies, and no redirects. HTTP and SOCKS5 without authentication and Basic HTTP proxy authentication are exercised with controlled local fixtures; HTTPS proxy certificate rejection is also tested. A successful HTTPS-proxy connection and the other authentication schemes have not been verified. SOCKS5 username/password authentication is unsupported. Basic authentication to an HTTP proxy is exposed on the network hop to that proxy; use an appropriately protected network. Proxy failure, an unavailable diagnostic endpoint, DNS, TLS and authentication may be indistinguishable in some cases, so errors do not establish which service failed. In particular, .NET can report a rejected CONNECT challenge as an ambiguous tunnel error without the proxy's HTTP status; the preflight does not claim a definite authentication failure in that case. An IP address displayed by the test is only what the endpoint reported, not proof of a public exit IP. The test does not exercise Chromium, UDP, DNS leak behavior or WebRTC. It cannot establish that browser traffic fails closed.

## Runtime investigation still required

The repository pins CefSharp 154.0.340. Its [versioned `IRequestContext` source](https://github.com/cefsharp/CefSharp/blob/v154.0.340/CefSharp/IRequestContext.cs) documents that preference operations require the CEF UI thread, and its [request handler source](https://github.com/cefsharp/CefSharp/blob/v154.0.340/CefSharp/Handler/RequestHandler.cs) exposes proxy challenge context. These APIs alone do not establish routing or isolation. The [Chromium proxy documentation](https://chromium.googlesource.com/chromium/src/+/main/net/docs/proxy.md) describes SOCKS5 as TCP-only and without SOCKS5 authentication in Chrome. It also describes implicit direct bypasses for localhost and link-local addresses, and security implications of overriding them. Confirm behavior against the pinned CEF runtime and controlled fixtures before supporting any transport or changing bypass rules. [Microsoft's DPAPI documentation](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection) describes the current-user protection boundary.

Later work must independently test proxy authentication scope, HTTP/HTTPS/SOCKS5 routing, redirects, subresources, popups, offline transitions, local bypass behavior, DNS, IPv4/IPv6, WebRTC and non-HTTP traffic. A successful connection test alone cannot prove absence of direct network traffic. OS-level containment may be required for stronger guarantees.

The Windows native suite contains a controlled, research-only CEF probe. It observes the default loopback bypass, then sets the special bypass-subtraction rule **only in the test process** to examine HTTP navigation, a redirect, a JavaScript subresource, a native popup and a stopped proxy through a loopback fixture. The local origin and proxy are independent listeners. The temporary test proxy forwards only GET requests to its one designated loopback origin; it does not forward browser headers or credentials and is not part of the application. This narrow observation does not enable production routing, test proxy authentication, establish behavior for other traffic or justify overriding Chromium's loopback security protections in production.

The pinned [CefSharp proxy helper](https://github.com/cefsharp/CefSharp/blob/v154.0.340/CefSharp/RequestContextExtensions.cs) lists HTTP and SOCKS schemes, but does not list HTTPS in its scheme validator. That does not by itself establish whether an HTTPS proxy works through a lower-level preference; it requires a separate native test.

The native HTTP-proxy probe also exercises a CONNECT tunnel to one synthetic HTTPS host. It first verifies the local TLS fixture using a custom root trusted only by a test client, then uses the production browser request handler to check rejection of that fixture's untrusted certificate. The fixture is not a general forwarding service and changes no system trust store. This covers certificate rejection for one HTTPS destination over an HTTP proxy; it does not establish successful HTTPS browsing, HTTPS-proxy transport, authentication or broader network isolation.

A second test-only probe exercises a Basic HTTP proxy challenge using fake credentials. Its callback applies a host, port, protocol and `isProxy` scope and caps credential submissions. A synthetic website challenge is canceled and checked for an `Authorization` header. The fixture never forwards requests, and the credentials and request headers are not logged. This is evidence about a test callback, not production proxy-authentication support. Basic authentication to an HTTP proxy is not encrypted between the browser and that proxy; an HTTPS proxy would require separate validation.

The routing probe also attempts to gather a WebRTC ICE candidate using a short-lived STUN listener on loopback. It reports whether it observed a STUN UDP packet without logging candidate addresses. No packet, an unavailable API, or a non-STUN packet is explicitly inconclusive; none proves absence of DNS or WebRTC leaks. The listener is test-only and sends no packets to a public STUN service.

On 2026-10-30, [Windows CI run 41057825104](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/41057825104), testing commit `b7e6cb403a267d5e8c1b39bd7f20a5fe25ec27ac`, observed a direct STUN UDP packet at that local listener while the controlled HTTP request used the proxy fixture. This shows the tested proxy preference alone did not contain all traffic in that environment; it does not characterize every WebRTC path or a public-network leak. The authentication fixture also received the synthetic `aegis-auth.invalid` target hostname as an HTTP proxy request. Neither observation monitors all DNS requests or establishes DNS isolation. Production proxy-required profiles remain blocked pending a design and independent tests for these paths.

The test process additionally checks whether CEF allows the `webrtc.ip_handling_policy` preference to be set to `disable_non_proxied_udp`, and, if so, repeats the local STUN observation. This does not change production settings or prove that other paths are contained. [Chromium's policy description](https://chromium.googlesource.com/chromium/src/+/376fc41e87a058f7a7b300b0ec3a4982b4ec0960/components/policy/resources/templates/policy_definitions/Miscellaneous/WebRtcIPHandling.yaml) describes limits on non-proxied UDP while allowing TCP behavior; supported behavior must be verified on the pinned runtime.

On 2026-10-31, [Windows CI run 41156105515](https://github.com/roshan-pandit1/AegisBrowser/actions/runs/41156105515), testing commit `b96273e1a596080ec42f440ffcc7a96e5ab1781c`, accepted that preference. The local listener observed STUN UDP before the change and no STUN packet during one observation afterward. The second result is inconclusive; it does not establish fail-closed behavior, cover WebRTC TCP or verify DNS.

## Manual Windows verification still required

- Run the opt-in preflight against an authorized proxy and a trusted HTTPS endpoint, cancel an in-progress test, and check the saved-revision and launch-block warnings at 100%, 150% and 200% scaling. Compare the observation with independent network measurements; the preflight does not exercise Chromium.
- On a test account, verify credential replacement and loss of access after moving protected data to a different Windows user.
- Test interrupted writes, corrupt/missing database, explicit Direct recovery and rollback to an older build using disposable profiles.
- Verify real proxy routing and failure transitions only after a browser integration PR provides controlled native network tests.
