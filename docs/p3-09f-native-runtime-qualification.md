# P3-09F: native runtime and sandbox qualification

This research is stacked on draft PR #51. It does not replace production CefSharp binaries or alter browser startup. **`OWNER_RELEASE_CONTRACT: UNSATISFIED`** and **`PRODUCTION_BINDING_READINESS: NOT_APPROVED`** remain in force. Source inspection, metadata checks, native loading, native startup, callback observations and security enforcement are separate kinds of evidence.

## Pinned inputs

The pinned inputs are CefSharp `154.0.340` at [`ec1027aa21e1af1217681a349104c15d29bbc21a`](https://github.com/cefsharp/CefSharp/tree/ec1027aa21e1af1217681a349104c15d29bbc21a), CEF `154.0.34+g14c5a08+chromium-154.0.8037.98` at [`14c5a089e8452874cb1a556dc3fde26ed2d87723`](https://github.com/chromiumembedded/cef/tree/14c5a089e8452874cb1a556dc3fde26ed2d87723), and `cef.sdk` 154.0.34. See the [P3-09E runbook](p3-09e-native-research.md) for the official SDK hash and isolated build. Version metadata and source pins do not themselves establish binary provenance, ABI equivalence, sandbox use or process restrictions.

## Framework metadata

The pinned native project targets `net6.0`. The official 154.0.340 runtime and a local source-built runtime both declare `.NETCoreApp,Version=v6.0`, but their assembly-reference lists differ: the official runtime references `System.Runtime` and `System.Runtime.CompilerServices.VisualC` 6.0, while the local VS 2026 build references version 8.0 for both, among other 6.0 references. The local assembly loaded for reflection in a .NET 8 x64 host; the .NET 6 host failed. A separate minimal C++/CLI project with no CefSharp reference reproduced the same local 8.0 references while targeting net6.0 with SDK 6.0.428 and the .NET 6 host input. This narrows the issue to the local toolchain or environment rather than a CefSharp dependency alone; it does not establish the exact cause or imply all VS 2026 builds are affected. A hosted VS 2022 x64 build of the pinned native project reported the net6.0 target and 6.0 versions for these references. These are metadata observations, not complete load or ABI verification. `FRAMEWORK_COMPATIBILITY: INCONCLUSIVE` until the mismatch and intended build are fully validated.

`tests/research/p309f/FrameworkMetadata` reads PE/CLI metadata without loading or executing the target. It reports the declared target and assembly references, and rejects framework-name references newer than a caller-supplied maximum major version. The check is deliberately narrow: assembly versions do not universally follow .NET major versions, and a pass does not establish complete dependency resolution, C++/CLI initialization, API or ABI compatibility. Run its isolated negative tests with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\research\p309f\test-framework-metadata.ps1`.

## Sandbox boundary

At the pinned source revision, CefSharp's `CefSettingsBase` initializes `no_sandbox` to true, its native initialize path passes a null Windows sandbox information pointer, and its subprocess path likewise passes null. This is source analysis, not a new application modification or a measurement of renderer tokens. Do not initialize an experimental browser with that setting and call it sandbox-qualified.

The [CEF Windows sandbox instructions](https://chromiumembedded.github.io/cef/sandbox_setup) require the browser and subprocess to use the same executable and pass sandbox information to both CEF execution and initialization. Since Chromium M138, CEF documents a bootstrap executable plus client DLL for builds outside the CEF/Chromium toolchain; an ordinary third-party build cannot assume the old static sandbox library is available. The exact CEF SDK contains the sandbox header but not the required bootstrap executable. A matching bootstrap and runtime must be sourced and checked separately. A non-null sandbox pointer or successful startup still does not independently establish renderer restrictions.

The read-only `inspect-sandbox-inputs.ps1` takes explicit absolute local bootstrap, client DLL and libcef paths plus independently approved SHA-256 pins. It checks file shape, x64 PE roles and the exact CEF file version without loading or executing any input. Matching caller-supplied pins produce `REVIEW_REQUIRED` and exit 2, with sandbox information, enforcement, startup and shutdown still unobserved; invalid or incomplete inputs return `BLOCKED_PRECHECK` and exit 1. Pins obtained from the same untrusted bundle are not a trust root. Its synthetic negative tests run via `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\research\p309f\test-sandbox-preflight.ps1`; they do not run CEF or verify a sandbox. Reparse and path checks are defense in depth, not protection against an administrator or concurrent hostile filesystem replacement.

## Isolated native host observations

The exact official CEF 154.0.34 Windows x64 minimal distribution includes `bootstrapc.exe`. The downloaded archive length was 172,752,666 bytes and matched the upstream index SHA-1 `BE54BBAF3222191DEC59FFD9C9EC7E8A7F44A26D`; this is a transfer check against upstream metadata, not independent publisher authentication. The extracted bootstrap's observed SHA-256 was `BD0D6DCF683171305C02BCEE6B6F5DAD2ABDD2F90FF8EF0593BE585E78E164C9`. The bootstrap and libcef were observed as not Authenticode-signed; these observations do not authenticate the files.

The test-only `tests/research/p309f/NativeHarness` client DLL requires explicit opt-in, a non-null bootstrap-supplied sandbox-information pointer, the pinned numeric bootstrap/runtime version, and rejects an explicit no-sandbox switch. It sets `no_sandbox` false and uses a synthetic local page. Its compile/link is isolated from production. These checks show what the client requested, not renderer token restrictions, correct subprocess cleanup, CefSharp compatibility or complete sandbox enforcement. The research workflow compiles the client; it does not automatically launch it.

Three bounded x64-under-ARM64 test attempts were made using the matching bootstrap and disposable caches. In the first, CEF context initialization and browser creation were logged, but no page-load completion arrived within 45 seconds. A normal close request was sent to the verified test-owned window; observed processes exited, but the client recorded incomplete shutdown and did not confirm `CefShutdown`. In the second, the client recorded `CEF_INITIALIZE_SUCCEEDED`, `BROWSER_CREATED`, a main-frame load error `-3`, `CLOSE_REQUESTED_AFTER_LOAD_ERROR`, `BEFORE_CLOSE`, and `CEF_SHUTDOWN: INCOMPLETE`. Its launcher did not obtain a reliable native exit code; the shell's zero exit is not a test pass. The third recorded initialization, browser creation and a cancelled navigation, but no fixture load completion before its 45-second timeout. After a normal close request to its revalidated test-owned window, it recorded `DO_CLOSE`, `BEFORE_CLOSE` and `CEF_SHUTDOWN_RETURNED`, while reporting a failed fixture and an undifferentiated sandbox-gate failure. Observed direct child processes exited; complete descendant cleanup and the native exit status were not independently established. A returned shutdown after timeout does not turn that attempt into a pass. Later client revisions distinguish fixture failure from an unexpected browser-lifetime fault; the observed test outcomes cannot be promoted to a successful complete lifecycle. These runs do not establish a renderer sandbox, a successful complete navigation or popup callback behavior. The non-sensitive logs are under the corresponding `aegis-p309f-native-run-*` temporary directories on the development host.

`test-run-result.ps1` tests a separate conservative transcript classifier. A timeout, missing or non-integer native exit code, failure marker, contradictory event ordering, or missing fixture-close event cannot become success. A matching transcript is labeled only as unauthenticated client claims and leaves sandbox enforcement, child cleanup and owner release unresolved. This is synthetic fault-injection coverage, not a native execution or a substitute for a process launcher that retains and checks its real exit status.

`SANDBOX_CONFIGURATION: REQUESTED` applies only to that client; `SANDBOX_ENFORCEMENT: INCONCLUSIVE`. Native popup creation, abortion, callback-target loss and the owner-release interleaving were not exercised. No isolated native-host observation certifies the CefSharp C++/CLI binding.

## Popup lifecycle and production boundary

The pinned CEF callback supplies an opener-scoped ID for popup approval and abortion, while successful creation identifies the created browser separately. The existing managed binding does not expose the native abort callback. CEF's abort routing re-finds the opener and may lose the route after registry removal; retaining the managed handler is insufficient by itself. The pinned CefSharp `CefFrameWrapper` also assumes the native client is a `ClientAdapter`, so a generic forwarding client requires a separate type-safety review. The exact terminal-delivery and host-lifetime conditions remain unresolved; a timeout, empty created-popup collection, or absent callback cannot establish safe release.

The experimental workflows and tests do not change production proxy enforcement, networking, TLS, popup admission or sandbox configuration. A sandbox-qualified native CEF host would provide evidence about that host; it would not automatically establish CefSharp binding compatibility or AppContainer/WFP containment. No experimental binding is approved for production.
