# Browser shutdown lifecycle: P3-09

The WinForms thread owns tab retirement state. A tab or window close registers the owner as retiring and starts one observer even if the browser is still initializing. Popup-close scheduling is idempotent, and requests for each observed popup are issued at most once on the CEF UI thread. A failed request is logged and the popup stays tracked until a real close callback; other popup requests can continue. A native close request is deferred until initialization and marked before dispatch, so a call that throws after uncertain delivery is not blindly repeated. During form close every tab is registered before any observer starts, and tab parents remain alive until all tracked native owners have closed. A callback from a native-initiated close is posted to the WinForms thread as a fallback; a prior explicit close already has an observer and does not depend on that post.

`RetirementRequest` tracks requests, not native completion. `OwnerCloseReady` means the life-span handler observed owner close readiness and its collection of created popups is empty. On the WinForms thread, `NativeHostRelease` waits for readiness, destroys the embedded host handle, and then waits for `OwnerClosed`. Only a completed release allows ordinary tab retirement. A ten-second warning reports that closure is still pending and does not cancel the underlying operation or authorize disposal. A missing readiness or owner-closed callback remains incomplete, including when a browser never initializes. A failed or uncertain close request likewise retains the owner and reports incomplete shutdown; there is no timeout-driven forced disposal.

CefSharp 154 documents life-span callbacks as CEF UI-thread callbacks and states that `DoClose` can be skipped when the associated OS window has already been destroyed; `OnBeforeClose` precedes browser destruction. See the [CEF 154 life-span contract](https://cef-builds.spotifycdn.com/docs/154.0/classCefLifeSpanHandler.html). If `OnBeforeClose` arrives without `DoClose`, the current readiness task may remain pending; this implementation intentionally does not infer safe host teardown. CEF and WinForms UI threads are distinct. The readiness task can complete before its posted WinForms notification, so the close request path checks the task first; a spontaneous CEF close racing the subsequent application request remains an unproven edge case.

The popup collection begins tracking at `OnAfterCreated`. An approved popup may still be in flight before that callback; an empty collection is not independent proof that no native popup creation is pending. Upstream CEF documents a popup-aborted event, but the installed CefSharp 154 life-span interface does not expose a corresponding documented callback or popup ID. This interval and missing popup close callbacks are unresolved. An external forced form disposal or Windows session teardown can bypass the normal cancellable form-close sequence and has not been verified. Spontaneous native-close notifications are retained across transient handle loss, subject to the dispatcher limitations below; explicit application close requests also start their own observer. No timeout is a native-close confirmation.

The offline `retirement-request-unit`, `native-release-unit` and `late-close-unit` modes test request idempotency, UI-thread ownership, deferred initialization, warnings and synthetic callback ordering without CEF. The `hwnd-repro` integration mode additionally exercises real CEF windows and an active popup on Windows CI. Deterministic task tests do not prove Chromium callback behavior, and a naturally missing native callback has not been reproduced. No browsing URLs or credentials are recorded by these diagnostics.

## P3-09B callback delivery and popup close

A keyed lifetime dispatcher retains close-start, close-ready and initialization notifications when a form handle is unavailable, and reschedules them after handle recreation. The WinForms thread alone drains actions; stale callbacks from a destroyed handle generation cannot consume pending work. Notifications coalesce by tab and kind. A failed post remains pending until a later notification or handle creation, and final form disposal drops pending work with a diagnostic. This is not a native-close signal and cannot restore a permanently disposed form. An action that throws is logged rather than blindly retried, because it may already have performed work.

A spontaneous owner `DoClose` now marks close-start, blocks later popup approval and requests closure of already-created popups before waiting for owner readiness. `OnBeforeClose` also signals close-start if `DoClose` did not run; the WinForms observer can then warn, but readiness remains unresolved and the host is not destroyed merely because close-start or owner-close was observed. The application checks close-start before issuing its own request; the cross-thread check-to-dispatch race is narrowed, not proven eliminated.

The installed CefSharp 154 `ILifeSpanHandler` does not expose the native CEF `OnBeforePopupAborted` callback or popup identifier. CEF permits popup creation to abort and documents that its abort callback can occur after the opener's `OnBeforeClose`. A previously approved popup may therefore still be untracked at readiness; blocking later approvals and closing a later observed popup do not prove that the owner was safe to release. No pending counter or timeout is used to invent a terminal event, and this safety gap remains open. See the [CEF 154 contract](https://cef-builds.spotifycdn.com/docs/154.0/classCefLifeSpanHandler.html). Forced form/session teardown and the native smoke harness's synthetic cleanup on timeout remain unverified; no naturally missing callback has been reproduced.

Deterministic callback characterization invokes the actual `SafePopups` handlers with synthetic browser proxies and a controlled scheduler. It covers tracked popups, a failed popup-close request while another proceeds, a late-created popup, repeated callbacks, `OnBeforeClose` without `DoClose`, and failed CEF task dispatch. The approved-before-creation interleaving demonstrates that readiness can be signaled before the late popup appears. The test reports this as a known limitation; it does not assert the owner was safe to destroy. An additional native CI scenario submits a popup request immediately before closing the form, but does not establish which callbacks won the race. The synthetic test harness still disposes its test form when an existing native test times out; that cleanup is not evidence that native shutdown succeeded.

## P3-09C source review and owner-release contract

The owner-release invariant is that the embedded host must not be destroyed while an approved popup might still depend on it, unless a documented native guarantee establishes safety. The current implementation **does not establish that invariant**: `OwnerCloseReady` is based on `DoClose` and the collection of popups observed in `OnAfterCreated`. A deterministic test can place an approved popup between those observations and show readiness before its later creation. The real CEF ordering has not been reproduced; absence in a bounded run would not prove it impossible.

The installed `CefSharp.Common.NETCore` 154.0.340 package identifies source commit [`ec1027aa21e1af1217681a349104c15d29bbc21a`](https://github.com/cefsharp/CefSharp/tree/ec1027aa21e1af1217681a349104c15d29bbc21a) and declares native runtime 154.0.34. At that source revision, [`ClientAdapter.h`](https://github.com/cefsharp/CefSharp/blob/ec1027aa21e1af1217681a349104c15d29bbc21a/CefSharp.Core.Runtime/Internals/ClientAdapter.h) receives native `popup_id` but does not override `OnBeforePopupAborted`, and [`ClientAdapter.cpp`](https://github.com/cefsharp/CefSharp/blob/ec1027aa21e1af1217681a349104c15d29bbc21a/CefSharp.Core.Runtime/Internals/ClientAdapter.cpp) forwards popup approval to the managed handler without that ID. The [managed interface](https://github.com/cefsharp/CefSharp/blob/ec1027aa21e1af1217681a349104c15d29bbc21a/CefSharp/Handler/ILifeSpanHandler.cs) exposes neither the abort callback nor popup ID, and `OnAfterCreated` does not supply that ID either.

The [CEF 154 reference](https://cef-builds.spotifycdn.com/docs/154.0/classCefLifeSpanHandler.html) states that successful allowed creation invokes `OnAfterCreated`; its `OnBeforePopup` description qualifies failed-creation abort notification on the opener not yet being destroyed. Its `OnBeforeClose` and abort descriptions also state that a pending abort notification can arrive after opener close, when the opener is invalid. Those statements do not establish an unconditional terminal notification available to this managed handler or a guarantee that popup creation resolves before `DoClose` or host destruction. The reference is CEF 154.0.1 documentation; byte-for-byte equivalence to the installed 154.0.34 native runtime has not been established. Life-span callbacks are documented on the CEF UI thread; WinForms control access remains on its own UI thread. A queued CEF task is not a documented popup-creation fence.

A managed pending counter cannot safely decrement an aborted popup without a terminal signal; retaining every owner after any approval would indefinitely prevent ordinary popup-enabled tabs from closing. Denying all popups would alter OAuth and opener behavior. A separate popup owner or native binding extension needs a separately reviewed ownership/ABI and build plan; merely adding an abort ID is insufficient because successful `OnAfterCreated` does not expose that ID. A candidate extension must cover abort delivery, managed callback-target lifetime after opener close, successful-creation association or a justified aggregate protocol, and build/package compatibility before it can gate host release. None is implemented here. The existing release decision remains an open safety defect, not a certified safe fallback. The app's normal popup policy and binaries are unchanged.

The Windows native harness now records bounded event kinds for one synthetic popup without URLs or profile content. It fails if it actually observes approval, owner readiness, then creation; a missing or differently ordered observation is explicitly inconclusive for other orderings. The deterministic callback characterization remains the reproducible regression target. Neither test establishes a native lifetime guarantee. The current spontaneous-close versus application-request check-to-dispatch race also remains unproven; moving host references across queued CEF work would itself require a verified managed/native lifetime contract.

## P3-09D: binding and terminal-correlation feasibility

**Status:** `BINDING_SOURCE_FEASIBILITY: INCONCLUSIVE`; `IDENTITY_CORRELATION: NOT_FEASIBLE_WITH_CURRENT_BINDING`; `POPUP_TERMINAL_CORRELATION: INCONCLUSIVE`; `OWNER_RELEASE_CONTRACT: UNSATISFIED`. These are distinct from the synthetic model tests below. No replacement runtime, native bridge, or production release gate is included.

The cached x64 `libcef.dll` file version is `154.0.34+g14c5a08+chromium-154.0.8037.98`; the NuGet dependency pins `chromiumembeddedframework.runtime` 154.0.34. Its exact [CEF source header at `14c5a08`](https://github.com/chromiumembedded/cef/blob/14c5a08/include/cef_life_span_handler.h) is more specific than the previously cited 154.0.1 reference. CefSharp.Common.NETCore 154.0.340 records [CefSharp commit `ec1027aa21e1af1217681a349104c15d29bbc21a`](https://github.com/cefsharp/CefSharp/tree/ec1027aa21e1af1217681a349104c15d29bbc21a) in its package metadata. Metadata and file version identify the intended correspondence; they do not independently authenticate the binary's provenance or prove byte-for-byte reproducibility.

The CEF callbacks execute on the CEF UI thread. `OnBeforePopup(opener, frame, popup_id, ...)` identifies the attempt within that opener; `OnBeforePopupAborted(opener, popup_id)` names an allowed attempt that failed before creation; `OnAfterCreated(created_browser)` supplies a browser identity, not the attempt ID. Browser and attempt IDs are different namespaces; the API does not state a reusable-ID lifetime suitable for a durable cross-owner key. A handler must not infer association from FIFO order, URL, timestamp, or a drained task queue. `OnBeforeClose` is not an abort-delivery fence: CEF describes later aborts when the opener is invalid, while its approval documentation also qualifies abort notification on the opener not having been destroyed. A creation abort is not the close of a created popup.

The exact [CEF popup manager](https://github.com/chromiumembedded/cef/blob/14c5a08/libcef/browser/browser_info_manager.cc#L180-L207) captures the opener browser ID and popup ID, deliberately avoids retaining the browser directly, and performs a later browser/client/handler lookup before invoking the abort callback. Its pending-popup destructor invokes the stored abort closure when creation did not complete; the browser lookup depends on the [registered browser information](https://github.com/chromiumembedded/cef/blob/14c5a08/libcef/browser/browser_host_base.cc#L223-L236). Thus retaining a managed handler or native adapter alone cannot guarantee delivery if that lookup no longer succeeds. `OnBeforeClose` alone does not establish that registry removal has already occurred. This is source-level evidence about that implementation, not a complete guarantee about every native path or when a lookup fails. A CEF UI task is not a documented creation barrier.

At the pinned revision [`ClientAdapter`](https://github.com/cefsharp/CefSharp/blob/ec1027aa21e1af1217681a349104c15d29bbc21a/CefSharp.Core.Runtime/Internals/ClientAdapter.h) is ref-counted and holds managed `gcroot` references to the browser control and adapter; `GetLifeSpanHandler` returns that native adapter. Its [callback implementation](https://github.com/cefsharp/CefSharp/blob/ec1027aa21e1af1217681a349104c15d29bbc21a/CefSharp.Core.Runtime/Internals/ClientAdapter.cpp) fetches the managed `LifeSpanHandler` from the control, discards the approval popup ID, and tracks created popups by browser identifier. The adapter does not override the abort callback. Retaining the adapter does not establish that the dynamically retrieved managed handler remains available: [WinForms control disposal clears it](https://github.com/cefsharp/CefSharp/blob/ec1027aa21e1af1217681a349104c15d29bbc21a/CefSharp.WinForms/ChromiumWebBrowser.cs#L391-L445). Nor can retention cause CEF to invoke a callback it cannot route. A correct bridge needs explicit ownership through terminal delivery, careful reference release and a result for delivery failure; no complete lifetime proof is available here.

| Candidate | Assessment |
| --- | --- |
| Forward only the native abort callback and ID | Insufficient: successful creation is not correlated, and abort delivery may be unavailable after opener lookup fails. |
| Count approvals, creations and aborts | Insufficient without proven one-for-one terminal delivery and unambiguous routing of every successful creation to its owner. Unknown or missing events must retain an unresolved state. |
| Per-attempt native `CefClient` forwarding proxy | A research candidate: [the pending-popup path stores the returned client](https://github.com/chromiumembedded/cef/blob/14c5a08/libcef/browser/browser_info_manager.cc#L321-L339), and [created-browser callbacks use that browser's client](https://github.com/chromiumembedded/cef/blob/14c5a08/libcef/browser/browser_host_base.cc#L1498-L1503). A unique proxy might carry attempt identity into its creation callback. It would need to forward every required handler, preserve native and managed ownership, cover nested/devtools popups and OAuth semantics, and still resolve missing abort delivery through the opener. No implementation or compatibility claim is made. |
| CEF-level terminal protocol or independent lifetime domain | Requires a separately reviewed native design and possibly upstream changes; the current public managed API provides no established complete predicate. |
| Reject all popups, force release, or assume quiet time means completion | Rejected: changes popup/OAuth behavior or invents terminal evidence. |

A candidate protocol must serialize admission and callback state on the CEF UI thread; bind each approval to its opener and attempt; retain a callback target for every possibly outstanding event; distinguish created browsers from aborted creations; wait for actual close of each created popup; and keep the WinForms owner alive while any safety-relevant state remains unknown. Duplicate, unknown, or conflicting events must not permit release. `OnBeforeClose`, a timeout, exception, missing callback, or successful task dispatch is not a terminal creation outcome. A close-ready signal is valid only after the owner close-start is observed **and** all relevant attempts have independently accounted terminal outcomes and all created popups have actually closed, subject to a separately established host-ownership contract. This predicate is a design requirement, not a claim that the installed binding can implement it.

The test-only `popup-correlation-model-unit` explores all possible pairings of unkeyed creation events with pending approvals. Under the deliberately hypothetical assumptions that all approvals, keyed aborts, creations and closures are completely and correctly delivered to one owner-lifetime scope, it shows that aggregate completion can sometimes be established without learning each successful attempt's identity. It rejects contradictory or lost event histories and does not infer completion from an absent event. Those delivery, scoping and ownership assumptions are exactly what remain unestablished for the installed binding; the model is neither a native bridge nor evidence that release is safe. It does not replace the actual-handler regression that reports `OWNER_RELEASE_CONTRACT: UNSATISFIED`.

Building a candidate requires the pinned CefSharp source, its matching CEF headers and x64 libraries, an appropriate Visual Studio/MSVC C++/CLI toolchain and Windows SDK, and the .NET build prerequisites from that source revision. A matching official runtime does not make a newly compiled adapter ABI-compatible by itself. A future isolated build must pin all inputs, document compiler/CRT and .NET dependencies, run x64 native load and shutdown tests, audit public interface compatibility and licensing, and assess redistribution and security maintenance before any package migration. Never substitute an experimental binary into the production browser based on synthetic tests. Full native bridge, ABI, and packaging validation remain NOT RUN; production binding readiness is NOT_APPROVED.
