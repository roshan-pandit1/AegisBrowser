# Zoom-aware viewport letterboxing

P4-FP-07 starts from PR [#70](https://github.com/roshan-pandit1/AegisBrowser/pull/70), commit `830ecfb658add6318ed03008a635b4331854ce53`. The production runtime remains .NET 8 and CefSharp 154.0.340 (Chromium 154.0.8037.98). The opt-in **Letterbox page viewport** setting is stored per profile, remains off by default, and changes take effect after the profile restarts. Normal tabs use the active setting; native popups are not letterboxed.

## Baseline and correction

The earlier controlled fixture measured a 1000×600 browser control as a 1000×600 CSS viewport at zoom level 0, but as 833×500 CSS pixels at zoom level +1. It also recorded a scrollable document whose `documentElement.clientWidth` differed from `innerWidth`. Those are observations from the stock runtime and fixture described in the [earlier viewport report](tor-css-viewport-verification.md), not evidence that every DPI or layout behaves the same way.

The zoom-aware calculation aims to choose centered control bounds corresponding to 200×100 CSS-pixel buckets at the browser's current zoom. Browsers can still be resized, zoomed and navigated normally; tiny panes retain their available dimensions when a full bucket cannot fit. Bounds are integer control units, so rounding and the relation between WinForms units and Chromium CSS pixels can limit precision. The implementation does not overwrite page APIs or fabricate screen dimensions.

## Verification and scope

The native fixture uses a controlled local page and disposable profiles. It measures the browser control and the page's `innerWidth`, `innerHeight`, `documentElement.clientWidth`, `documentElement.clientHeight`, `devicePixelRatio` and visual viewport where available. Zoom, resize, tab lifecycle, navigation and restart must be attributed to an actual browser result; a geometry unit test alone is not evidence of CSS behavior. Record unavailable measurements and shutdown failures instead of treating them as success.

On the Windows ARM64 development host using x64 CEF emulation and effective `DeviceDpi=96`, the unchanged parent fixture measured the zoom +1 letterboxed tab at 833×500 `innerWidth`/`innerHeight`, with a 1000×600 control and 1075×632 available area. With the correction and the same available area, zoom +1 measured 800×500 with a centered 960×600 control. Letterboxing disabled at that available area measured 896×527. The corrected zoom −1 case measured 1200×699 against a nominal 1200×700 bucket; integer control sizing accounts for the one-pixel difference. At zoom +1 the scrollable document's `clientWidth` was 787 and `visualViewport.width` approximately 787.5, so those dimensions are not represented as bucketed.

The final local native fixture passed 120 checks in its write process and 99 after profile restart; both exited 0 and reported CEF shutdown. At 110% zoom it measured 800×500 CSS with an 880×550 control. It exercised zoom +1/−1/reset, resizing and navigation while zoomed, tab switching, maximize/restore, and controlled form, dialog, scroll, media-control and iframe behavior. These are bounded fixture observations, not general website compatibility or popup layout evidence. The local Release x64 build succeeded with `NU1900` warnings because NuGet vulnerability metadata was unavailable. Final-head Windows CI remains pending until its runs complete.

Two subsequent local runs of intermediate revisions timed out waiting for native form closure immediately after the letterboxing-disabled zoom reset and exited 1. The disabled form did not run the new letterboxing timer. Waiting for the renderer's viewport to reflect the reset did not eliminate the second timeout. The final local run passed, but the cause of those timeouts remains unknown. Another intermediate enabled-only experiment stalled; source review found that its timer disposed CefSharp's cached browser-owned host wrapper. That disposal was removed. A further run using that incorrect ownership strategy was stopped before completion; it is not counted as passing evidence.

Zoom is polled for the selected tab, so the corrected bounds are eventual: a page can observe an earlier viewport during startup, navigation or immediately after a zoom change. Background tabs are refreshed when selected. If a zoom query stalls, its tab is not queried repeatedly and another selected tab can still be queried; the stalled tab's adjustment is not guaranteed.

Tests at one effective DPI do not establish behavior at 125%, 150%, 200%, or across differently scaled monitors. Scrollbars may make client and visual viewport widths differ from `innerWidth`; zoom and integer rounding may also create deviations. Native popup layout is outside the tab letterboxing implementation.

## Privacy and compatibility

The feature may reduce the number of viewport-size variants in tested scenarios, but a sample does not establish anonymity, cross-site unlinkability or complete fingerprint resistance. Pages can still observe screen dimensions, graphics, fonts, audio, IP addresses and other characteristics. Centered margins reduce available space and can change responsive layout; users can turn the option off and restart the profile. The feature does not alter Canvas, WebGL, device identity, networking, the Chromium sandbox, TLS verification or permission policy.

Local Font Access and CSS font-metric exposure are separate surfaces. A disposable stock CEF probe with the production `OriginPermissions` handler and an in-process HTTPS scheme fixture measured a fresh Local Fonts default and site setting of `Ask`, with JavaScript permission state `prompt`; a no-gesture `queryLocalFonts()` call rejected with `SecurityError`. A test-owned site-specific `Allow` produced `granted` and a resolved call; changing the default to `Block` left that site's setting `Allow`, its JavaScript permission state `granted`, and the call still resolved. A site `Block` read back as `Block` and the permission state as `denied`, but the call unexpectedly resolved in this fixture, including after navigation and when the block preceded the allow. Its cause remains unresolved. The probe exited 0 and reported CEF shutdown; it recorded no font names. It did not exercise real TLS, a genuine user gesture or establish whether a font permission prompt reaches the handler. The existing handler denies unsupported prompt types, but a default-only block cannot honestly promise to override retained site grants. No new font-access protection or permission behavior is claimed by this viewport change.
